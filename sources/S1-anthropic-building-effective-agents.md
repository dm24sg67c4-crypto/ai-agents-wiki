## 要點（引用時請用編號，例如 [S1.3]）

- **S1.1** Anthropic 把各種做法統稱為 agentic systems，並區分兩種架構：workflows 是 LLM 與工具透過「預先寫好的程式路徑」被編排；agents 則是 LLM 動態決定自己的流程與工具使用，自己掌控如何完成任務。
- **S1.2** agentic 系統的基本單元是 augmented LLM：LLM 加上檢索、工具、記憶等增強能力，模型能自己產生搜尋查詢、挑選工具、決定要保留哪些資訊。
- **S1.3** 建議先找最簡單的解法，必要時才增加複雜度，甚至可能根本不需要 agentic 系統；agentic 系統通常拿延遲與成本換取更好的任務表現。文中進一步說，workflow 對定義清楚的任務能提供可預測性與一致性，而需要彈性、且要大規模由模型自行決策時，agent 是比較好的選擇。
- **S1.4** 文中列出五種 workflow 模式：prompt chaining（把任務拆成固定順序，可在中間加程式檢查「gate」）、routing（分類後導向專門流程）、parallelization（分段或投票）、orchestrator-workers（中央 LLM 動態拆解任務、分派給工作者 LLM，再彙整結果）、evaluator-optimizer（一個 LLM 生成、另一個評估並回饋，形成迴圈）。
- **S1.5** evaluator-optimizer 適合「有明確評估標準、且反覆修正能帶來可衡量價值」的情境。
- **S1.6** Agent 先由人類下達指令或對話釐清任務，之後自行規劃並執行；執行中每一步都要從環境取得「ground truth」（例如工具回傳結果、程式執行結果）來判斷進度，並可在檢查點或遇到阻礙時暫停詢問人，也常設定停止條件（例如最大迭代次數）。
- **S1.7** Agent 的實作往往很單純：就是 LLM 依環境回饋，在迴圈中使用工具。因此工具集與工具文件的設計非常關鍵。
- **S1.8** Agent 的自主性意味著成本較高、錯誤可能累積；建議在沙盒中大量測試，並加上適當護欄。
- **S1.9** 三項核心原則：保持簡單、透明（明確呈現 agent 的規劃步驟）、用完整的工具文件與測試精心設計 agent-computer interface。
- **S1.10** 文中認為客服與程式開發是兩個特別適合 agent 的應用：客服需要對話加上行動、成功可衡量；程式的結果可用自動化測試驗證，但人工審查仍然重要。文中並指出，agent 最能發揮價值的任務通常需要對話與行動兼具、有清楚的成功標準、能建立回饋迴圈，並納入有意義的人類監督。
- **S1.11** 建議開發者先直接用 LLM API，框架雖然上手快，但多一層抽象會遮蔽底層 prompt 與回應、增加除錯難度。
